# Measurements

Raw data behind every number in the top-level README. Twelve runs, 30 button presses each, recorded on one
STM32F407G-DISC1 board at 230400 baud with SystemView tracing compiled in.

| Folder | Frame format | Firmware build |
|---|---|---|
| `ascii64/` | Fixed 64-byte ASCII lines for every message | `PROTOCOL_COMPACT=0`, `USE_SYSVIEW=1` |
| `compact/` | TEL 19 B / BTN 20 B binary frames with CRC-8; other messages stay 64-byte ASCII | `PROTOCOL_COMPACT=1`, `USE_SYSVIEW=1` |

`experiment_log.csv` indexes every run, every SystemView trace and the min/median/max events picked from each trace,
with the file paths, timestamps and data-quality notes.

## Run names

`<variant><flags>_S<n>`, for example `BTK_S6`:

| Part | Meaning |
|---|---|
| `A` / `B` / `C` | Scheduling variant (see the top-level README) |
| `T` | SystemView tracing compiled in (`USE_SYSVIEW=1`) |
| `K` | Compact binary frames (`PROTOCOL_COMPACT=1`) |
| `F` | ISR fast path (`BTN_FAST_PATH=1`), not used in these runs |
| `S5` / `S6` | Load scenario: 100 Hz telemetry + 5 ms CPU work / burst of 4 telemetry frames every 100 ms |

The board reports the same letters in its `ACK` line, and the ground station names the files after them.
A run therefore cannot be filed under the wrong configuration.

## Files per run

### `<run>.csv`: one row per button press

| Column | Description |
|---|---|
| `scenario` | `S5` or `S6` |
| `event_id` | Press ID assigned in the EXTI0 ISR (monotonic since boot) |
| `t0_us` | EXTI0 ISR entry: the accepted press edge |
| `t1_us` | ButtonTask received the event |
| `t2_us` | BTN message built, about to enter the TX queue |
| `t3_us` | UartTxTask about to start the transfer |
| `t4_us` | USART2 transmission-complete (TC) interrupt: the last stop bit has left the pin |
| `status` | `ok`, `drop`, `tx_error` or `timeout` |
| `note` | `warmup` (press inside the 5 s warm-up) or `short_interval` (< 0.5 s after the previous press) |

All timestamps come from one free-running 32-bit TIM2 counter at 1 MHz. Differences are taken modulo 2³²
(wrap after ~71.6 min). A timestamp that was never reached is left empty, not written as 0.

### `<run>_counters.csv`: window counters, `name,value`

Board counters dumped at the end of the measurement window:

- **Button:** `accepted`, `repeat` (bounce edges rejected by the filter).
- **Drops:** `btn_queue_drop`, `tx_queue_drop`, `pool_overflow`, `droplog_overflow`.
- **TX path health:** `tx_queue_max`, `tx_timeout`, `tx_start_fail`, `spurious_tc`, `encode_error`.
- **Telemetry:** `tel_sent`, `tel_drop`, measured period `tel_period_min/avg/max_us`, queue wait `tel_wait_avg/max_us`.
- **Stacks:** high-water marks `stack_hwm_*`, in words of free stack.

Lines prefixed `host_` come from the ground station:
- `host_seq_gaps`: lost live frames, detected from the sequence numbers.
- `host_line_errors`: corrupt frames.
- `host_rec_received` / `host_rec_expected`: records received versus expected, checked against the board's `END` line.

### `<run>_raw.txt`: complete serial session

Every line received from the board, starting at the `ACK` that opened the window. Binary frames are logged as hex,
followed by their decoded text. The dump after the window follows:

- `REC`: per-event records, with stage durations relative to t0.
- `CNT`: counters.
- `END`: the number of `REC` lines sent.

### `summary.csv`

Generated by `analysis/analyze.py` from the files above. Do not edit it by hand: CI recomputes it and fails if the
committed copy differs.

## Data-quality notes

These issues are also recorded in `experiment_log.csv`. The affected runs are kept rather than silently re-recorded:

- **`ascii64/AT_S5`:** the board reset inside the window. The first three presses came 2.2 / 3.4 / 4.5 s after boot,
  inside the 5 s warm-up.
- **`compact/ATK_S5`:** the window contains five board resets. Every press is ≥ 16.6 s after the last boot.
  The measured telemetry rate (90.7 Hz instead of 100 Hz) reflects the resets.
